# نصب روی سرور اختصاصی (Ubuntu/Debian)

این پوشه یک نصب‌کنندهٔ تعاملی دارد که «همگام» را روی سرور خودتان بالا می‌آورد:
دامنه، گواهی SSL رایگان، nginx، فشرده‌سازی، هدرهای امنیتی و کش درست؛ همه
به‌صورت خودکار، با تست سلامت در پایان.

اگر GitHub Pages برایتان کافی است، به این پوشه نیازی ندارید.

---

## چرا سرور اختصاصی؟

|                    | GitHub Pages      | سرور اختصاصی         |
| ------------------ | ----------------- | -------------------- |
| راه‌اندازی         | آماده             | یک بار اجرای اسکریپت |
| دامنهٔ اختصاصی     | ممکن است          | کامل، با SSL خودکار  |
| سرو از ریشهٔ دامنه | نه (زیرمسیر)      | بله                  |
| کنترل هدرها و کش   | محدود             | کامل                 |
| به‌روزرسانی        | خودکار با هر push | `--update`           |

هر دو کاملاً کار می‌کنند؛ سرور اختصاصی کنترل بیشتری می‌دهد.

نصب‌کننده، همهٔ پیام‌های ترمینال را انگلیسی می‌نویسد و با ارقام لاتین کار
می‌کند؛ رابط فارسی خودِ برنامه تغییری نکرده است.

---

## پیش‌نیازها

- سرور Ubuntu 22.04 یا 24.04 (یا Debian 12) با دسترسی root یا `sudo`
- دامنه‌ای که رکورد `A` آن به IP سرور اشاره کند
- پورت‌های ۸۰ و ۴۴۳ آزاد (اگر Apache دارید، اول متوقفش کنید)
- حدود ۱٫۵ گیگابایت فضای دیسک آزاد؛ برای ساخت swap خودکار، دست‌کم ۴ گیبی‌بایت
- برای ساخت روی سرور با رم کمتر از ۱۵۳۶ مبی‌بایت، دست‌کم ۱۰۲۴ مبی‌بایت swap آزاد
  و قابل‌استفاده؛ جزئیات در بخش «سرور کم‌حافظه» آمده است

HTTPS اجباری است، نه اختیاری: بدون HTTPS مرورگر سرویس‌ورکر را ثبت نمی‌کند،
پس حالت آفلاین و «افزودن به صفحهٔ اصلی» کار نمی‌کند.

## اجرا

مخزن را روی سرور بگیرید و اسکریپت را اجرا کنید:

```bash
git clone https://github.com/saeedgh837/fit-tracker-pwa.git && cd fit-tracker-pwa && sudo bash deploy/install.sh
```

اسکریپت این مقادیر را می‌پرسد و برای هرکدام پیش‌فرض پیشنهاد می‌دهد:

- **دامنهٔ سایت**: مثل `fit.example.com` (بدون `https://`)
- **ایمیل**: برای Let's Encrypt؛ فقط برای یادآوری انقضای گواهی
- **مسیر نگهداری نسخه‌ها**: پیش‌فرض `/var/www/hamgam`
- **حالت تامین سورس**: `git` (پیش‌فرض)، `local` یا `prebuilt`

سپس ۱۰ گام را پیش می‌برد: بررسی سیستم، نصب بسته‌ها، ساخت برنامه، استقرار،
تنظیم nginx، فایروال، گواهی SSL، و ۱۲ بررسی سلامت. اگر همه‌چیز درست باشد،
بنر سبز «نصب با موفقیت کامل شد» را با نشانی سایت می‌بینید.

### حالت‌های دیگر

```bash
sudo bash deploy/install.sh --non-interactive --domain fit.example.com --email me@example.com
```

```bash
sudo bash deploy/install.sh --update
```

```bash
sudo bash deploy/install.sh --rollback
```

`--help` فهرست کامل گزینه‌ها را نشان می‌دهد.

## گواهی SSL دستی

اگر گواهی را خودتان می‌گیرید یا از صادرکنندهٔ دیگری دارید، لازم نیست Certbot
وارد شود. مسیر زنجیرهٔ کامل و کلید خصوصی را بدهید:

```bash
sudo bash deploy/install.sh --tls-cert /etc/ssl/hamgam/fullchain.pem --tls-key /etc/ssl/hamgam/privkey.pem
```

دادن هر دو مسیر با هم، حالت `manual` را انتخاب می‌کند. سه حالت وجود دارد:

| حالت     | چه می‌کند                                     |
| -------- | --------------------------------------------- |
| `auto`   | Certbot گواهی Let's Encrypt می‌گیرد (پیش‌فرض) |
| `manual` | از فایل‌های موجود شما استفاده می‌کند          |
| `off`    | بدون HTTPS؛ نام قدیمی آن `--skip-tls` است     |

- در اجرای تعاملی، حالت پرسیده می‌شود و در حالت دستی مسیر هر دو فایل.
- ایمیل فقط برای صدور خودکار لازم است؛ حالت دستی به Certbot و ایمیل کاری ندارد.
- حالت و مسیرها در `/etc/hamgam/install.conf` ذخیره می‌شوند، نه محتوای کلید.
  اجرای بعدی `--update` بدون گزینهٔ تازه، همان انتخاب را نگه می‌دارد.
- `--tls-mode` صریح بر مقدار ذخیره‌شده اولویت دارد. ترکیب متناقض، مثل
  `--tls-mode auto` همراه با مسیر فایل، خطاست؛ نه یک اولویت مبهم.

### پیش از استقرار چه چیزی بررسی می‌شود

نصب‌کننده پیش از تغییر nginx این‌ها را می‌سنجد و در هر موردی می‌ایستد:

- فایل گواهی و کلید هر دو موجود، خواندنی و PEM معتبر باشند.
- مسیرها مطلق باشند و نویسه‌ای نداشته باشند که بتواند کانفیگ nginx را بشکند.
- کلید رمزدار نباشد؛ نصب غیرتعاملی نمی‌تواند رمز بپرسد.
- کلید عمومی گواهی و کلید خصوصی یکی باشند، برای RSA و ECDSA.
- زنجیرهٔ کامل و مرتب از برگ تا ریشه باشد و `serverAuth` داشته باشد.
- گواهی دامنهٔ اصلی و همهٔ دامنه‌های اضافه را پوشش دهد، با تاریخ معتبر.
- فایل‌ها و همهٔ پوشه‌های والدشان مالک root باشند و کاربر دیگری نتواند
  جای‌شان را بگیرد. کلید خصوصی باید مود `600` یا `400` داشته باشد.
- مسیرها بیرون از پوشه‌های برنامه و تنظیمات همگام باشند؛ وگرنه حذف نصب
  گواهی شما را با خودش می‌برد.

اعتبار زنجیره با OpenSSL بررسی می‌شود، نه با `curl -k`. گواهی self-signed یا
Cloudflare Origin به‌طور پیش‌فرض «مورداعتماد مرورگر» حساب نمی‌شود؛ اگر ریشهٔ
آن صادرکننده در مخزن گواهی سرور نصب شده باشد، بررسی موفق می‌شود.

مسیرهایی که می‌دهید نه کپی می‌شوند نه مجوزشان عوض می‌شود؛ nginx مستقیم به
همان فایل‌ها اشاره می‌کند. اگر فایل را جابه‌جا کردید، مسیر تازه را در اجرای
بعدی بدهید یا `install.conf` را با اجرای دوبارهٔ اسکریپت به‌روز کنید.

### تمدید گواهی دستی

تمدید و پایش انقضا کار شماست. هر بار که گواهی تازه شد:

۱. جفت تازه را در همان مسیر بنویسید؛ لازم نیست نام فایل عوض شود.
۲. با `sudo nginx -t` کانفیگ را بررسی کنید.
۳. `sudo systemctl reload nginx` را اجرا کنید.

**نگه‌داشتن گواهی قبلی در حافظهٔ nginx کافی نیست.** با نخستین ری‌استارت،
همان گواهی کهنه برمی‌گردد. پس از هر تمدید باید `reload` انجام شود.

اسکریپت در هر `--update` جفت را دوباره اعتبارسنجی و nginx را reload می‌کند،
ولی تمدید را برای شما زمان‌بندی نمی‌کند. توصیهٔ Certbot در پایان نصب هم در
حالت دستی نمایش داده نمی‌شود.

اگر مسیر گواهی عوض شد، جفت قبلی را پاک نکنید تا `nginx -t` و reload تازه
موفق شود. در صورت شکست، nginx می‌تواند با تنظیم پیشین ادامه دهد.

### گواهی دستی و پورت اشغال‌شده

اگر پورت ۸۰ یا ۴۴۳ را سرویس دیگری، مثل Xray، گرفته باشد، گواهی دستی این
مشکل را حل نمی‌کند. nginx نمی‌تواند روی پورتی گوش دهد که در اختیار دیگری
است، و سایت هم بالا نمی‌آید. اول تعارض پورت را حل کنید:

```bash
sudo ss -ltnp | grep -E ':(80|443) '
```

نام سرویس و PID را نشان می‌دهد. آن سرویس را متوقف کنید یا nginx را به
پورت دیگری ببرید؛ گواهی، جدا از این موضوع است.

## حذف نصب

```bash
sudo bash deploy/install.sh --uninstall --dry-run
```

```bash
sudo bash deploy/install.sh --uninstall
```

حالت `--dry-run` فقط فهرست اهداف و موارد باقی‌مانده را نشان می‌دهد: هیچ فایلی
حذف یا جابه‌جا نمی‌شود و nginx هم reload نمی‌شود. اجرای عادی اول همین فهرست
را نشان می‌دهد و بعد تایید می‌گیرد.

در حالت غیرتعاملی، حذف بدون `--yes` انجام نمی‌شود:

```bash
sudo bash deploy/install.sh --uninstall --non-interactive --yes
```

`--uninstall` با `--update`، `--rollback` و گزینه‌های نصب جمع نمی‌شود.
به آزادبودن پورت، DNS، npm، build، apt یا فایل گواهی سالم هم کاری ندارد؛
حذف از همهٔ این‌ها مستقل است.

### چه چیزی پاک می‌شود

نصب‌کننده فهرست کوچکی از آنچه واقعاً ساخته در `/etc/hamgam/owned.tsv` نگه
می‌دارد و فقط همان را حذف می‌کند:

- پوشهٔ نسخه‌ها و پیوند `current`
- کانفیگ سایت nginx، snippet هدرها و نقشهٔ کش
- فایل تنظیمات و لاگ نصب
- لاگ‌های اختصاصی همگام در `/var/log/nginx/`

پوشه، فایل یا سرویسی که خودش نساخته، حذف نمی‌کند.

### چه چیزی می‌ماند

- **گواهی و کلید دستی شما.** فایل‌های خارجی هرگز پاک نمی‌شوند.
- سایت‌های دیگر nginx، Xray و قواعد فایروال. nginx هم متوقف نمی‌شود؛ اگر
  سایت دیگری روی آن باشد، به کارش ادامه می‌دهد.
- بسته‌های مشترک مثل nginx، Node و Certbot، و timer تمدید Certbot.
- مخزن محلی و ورودی `prebuilt`.
- **swap.** فایل swap فعال یا با وضعیت نامعلوم نه حذف می‌شود نه `swapoff`؛
  `/etc/fstab` هم دست‌نخورده می‌ماند. مسیر و وضعیت swap باقی‌مانده در گزارش
  پایانی می‌آید. ادعای «هیچ اثری نمانده» درست نیست و اسکریپت هم چنین ادعایی
  نمی‌کند.

### وقتی حذف کامل نمی‌شود

اگر کانفیگ nginx دستی تغییر کرده باشد، یا سایت دیگری به آن وابسته باشد،
یا `nginx -t` و reload موفق نشوند، حذف متوقف می‌شود. فایل کانفیگ به حالت
قبلی برمی‌گردد، پوشهٔ سرو‌شده می‌ماند و کد خروج غیرصفر است. پیام پایانی
دقیقاً می‌گوید چه چیزی باقی ماند؛ موفقیت کامل اعلام نمی‌شود.

اگر پوشه‌ای هنوز در خروجی `nginx -T` ارجاع داشته باشد، همان پوشه حذف نشدنی
است و نگه داشته می‌شود.

### نصب‌های قدیمی

نصب‌هایی که پیش از نسخهٔ `2.2.0` انجام شده‌اند فهرست مالکیت ندارند. حذف
خودکار برای آن‌ها انجام نمی‌شود: نام پوشه یا مالک root به‌تنهایی دلیل کافی
نیست. اگر مطمئنید مسیرها متعلق به همان نصب است، صریحاً بگویید:

```bash
sudo bash deploy/install.sh --uninstall --adopt-legacy
```

`--yes` به‌تنهایی هیچ مسیری را به فهرست مالکیت اضافه نمی‌کند. مسیرهای مبهم
نگه داشته و در گزارش به‌عنوان حذف‌نشده اعلام می‌شوند.

اجرای دوبارهٔ `--uninstall` روی نصب پاک‌شده بی‌خطر است و چیزی را خراب نمی‌کند.

## ساختار استقرار

فایل‌ها هرگز مستقیم روی نسخهٔ زنده کپی نمی‌شوند:

```
/var/www/hamgam/
├── releases/
│ ├── 20261019-010203-a1b2c3d/ ← یک نسخهٔ کامل و مستقل
│ └── 20261018-220904-819575b/ ← نسخهٔ پیشین
├── current -> releases/20261019-... ← پیوند اتمیک؛ ریشهٔ nginx همین است
└── .previous ← نسخه‌ای که --rollback به آن برمی‌گردد
```

چرا این‌قدر مهم است:

- **هیچ‌وقت نسخهٔ نیمه‌کپی‌شده روی سایت نیست.** هر اجرا اول یک نسخهٔ کامل
  می‌سازد و بعد پیوند را جابه‌جا می‌کند. جابه‌جایی پیوند یک عملیات اتمیک است.
- **تب‌های باز نمی‌شکنند.** فایل‌های هش‌دار نسخهٔ پیشین در نسخهٔ تازه نگه
  داشته می‌شوند، پس اگر کاربری هنوز نسخهٔ قدیمی را اجرا می‌کند و یک chunk
  تنبل را می‌خواهد، ۴۰۴ نمی‌گیرد.
- **بازگردانی خودکار هنگام خطای غیرمنتظره.** اگر بعد از جابه‌جایی پیوند خطایی
  رخ دهد، اسکریپت خودش به نسخهٔ پیشین برمی‌گردد. اگر تست سلامت پایان کار رد
  شود، نسخهٔ تازه روی سایت می‌ماند و اسکریپت دستور `--rollback` را چاپ می‌کند.
- **پاک‌سازی امن.** فقط چند نسخهٔ آخر می‌مانند، و نسخهٔ فعال و هدف بازگردانی
  هرگز پاک نمی‌شوند.

## فایل‌هایی که ساخته می‌شود

| مسیر                                      | چیست                            |
| ----------------------------------------- | ------------------------------- |
| `/var/www/hamgam/`                        | نسخه‌ها و پیوند `current`       |
| `/etc/nginx/sites-available/hamgam`       | کانفیگ سایت                     |
| `/etc/nginx/snippets/hamgam-headers.conf` | هدرهای امنیتی                   |
| `/etc/nginx/conf.d/hamgam-cache.conf`     | سیاست کش                        |
| `/etc/hamgam/install.conf`                | تنظیمات نصب (فقط root، مود ۶۰۰) |
| `/etc/hamgam/owned.tsv`                   | فهرست منابعی که نصب‌کننده ساخته |
| `/var/log/hamgam-install.log`             | لاگ کامل نصب                    |

تنظیمات ذخیره‌شده و فهرست مالکیت هیچ رمز یا کلیدی ندارند. مسیر گواهی و کلید
دستی در تنظیمات می‌آید، ولی محتوای فایل‌ها نه.

## نکات امنیتی و رفتار محافظه‌کارانه

اسکریپت عامدانه در چند جا محافظه‌کار است:

- **فایروال را خودش روشن نمی‌کند.** روشن‌کردن `ufw` می‌تواند دسترسی SSH را
  قطع کند. اگر `ufw` فعال باشد فقط پورت‌های ۸۰ و ۴۴۳ را باز می‌کند.
- **کانفیگ پیش‌فرض nginx را بی‌اجازه حذف نمی‌کند.** ممکن است سرویس دیگری از
  آن استفاده کند؛ تایید می‌گیرد و راه بازگردانی را چاپ می‌کند.
- **کانفیگی که certbot نوشته را با قالب HTTP بازنویسی نمی‌کند**، وگرنه گواهی
  بی‌اثر می‌شد.
- **`npm ci` و build را با کاربر غیرریشه اجرا می‌کند** تا اسکریپت‌های lifecycle
  وابستگی‌ها دسترسی root نگیرند. اگر کاربر غیرریشه‌ای در دسترس نباشد، هشدار
  می‌دهد و همان‌جا build را با root ادامه می‌دهد.
- **nginx از snap را تشخیص می‌دهد و پیش از هر تغییری متوقف می‌شود**، چون دو
  نصب موازی nginx سرور را خراب می‌کند.
- **مسیرهای سیستمی را نمی‌پذیرد.** `/`، `/etc`، `/usr` و مانند آن‌ها رد
  می‌شوند تا اشتباه تایپی به پاک‌شدن فایل‌های سیستمی منجر نشود.
- **هر اجرا قفل می‌شود** تا دو اجرای همزمان با هم تعارض نکنند.

### Cloudflare

اگر دامنه پشت پروکسی Cloudflare است:

- حالت SSL را روی **Full (strict)** بگذارید، نه Flexible. با Flexible،
  Cloudflare به سرور شما HTTP حرف می‌زند و ریدایرکت HTTPS بی‌پایان می‌شود.
- برای گرفتن گواهی با `DNS-01`:

```bash
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini -d fit.example.com
```

فایل مجوز باید فقط برای root خواندنی باشد:

```bash
sudo chmod 600 /etc/letsencrypt/cloudflare.ini
```

- بررسی DNS در اسکریپت فقط **تشخیصی** است و جلوی گرفتن گواهی را نمی‌گیرد،
  چون پشت Cloudflare یا NAT آدرس دیده‌شده با IP سرور یکی نیست.




تست‌های TLS با OpenSSL واقعی کار می‌کنند: یک CA موقت در پوشهٔ تست ساخته
می‌شود و برگ‌های RSA و ECDSA امضا می‌شوند. کلید نامطابق، SAN نادرست، گواهی
منقضی یا نامعتبر، کلید رمزدار، مجوز ناامن و گواهی نامورداعتماد رد می‌شوند.
خروجی واقعی `render_site_config` و بازگردانی کانفیگ هنگام شکست `nginx -t`
و reload هم بررسی می‌شود. هیچ‌کدام از این تست‌ها مخزن گواهی سیستم را تغییر
نمی‌دهد.

تست‌های حذف، مسیرهای خطرناک، symlink، فهرست مالکیت، تایید غیرتعاملی و
سناریوهای شکست reload را پوشش می‌دهند. فایل‌های شاهد بیرون از پوشهٔ برنامه
ساخته می‌شوند و باید پس از حذف دست‌نخورده بمانند.

این دو suite نیاز به root دارند، چون مجوز فایل‌ها و مالکیت پوشه‌ها را
واقعی بررسی می‌کنند. روی Git Bash ویندوز معنی ندارند؛ لینوکس لازم است.

تست‌های حافظه بدون فعال‌کردن swap واقعی، سیاست اجازه، محدودیت‌های والد cgroup،
حفظ کد خروج، مسیرهای ناامن و پاک‌سازی فایل ناقصِ غیرفعال را بررسی می‌کنند.

تست‌های واحد برای توابع خالص و کانفیگ تولیدشده: اعتبارسنجی ورودی، جابه‌جایی
اتمیک، بازگردانی، مهاجرت از چیدمان قدیمی، نگه‌داشتن asset های نسخهٔ پیشین،
پاک‌سازی نسخه‌ها، و اعتبارسنجی خروجی build.

اجرای واقعی روی اوبونتو در ورک‌فلوی `installer.yml` انجام می‌شود: نصب کامل با
apt و nginx واقعی، بررسی سایت زنده، اجرای دوباره برای اثبات idempotent بودن،
به‌روزرسانی، بازگردانی، و زنده‌ماندن سایت بعد از ری‌استارت nginx. همان ورک‌فلو
با یک CA موقت، گذر به گواهی دستی و حذف کامل را هم روی nginx واقعی می‌آزماید:
سایت شاهد روی پورت دیگر باید زنده بماند و گواهی و `/etc/fstab` دست‌نخورده.

## عیب‌یابی

**گواهی گرفته نشد.** اسکریپت در پایان صریح می‌گوید. معمولاً یکی از این‌هاست:

- رکورد A دامنه به این سرور اشاره نمی‌کند
- پورت ۸۰ از بیرون بسته است (فایروال ابری یا NAT)
- دامنه پشت Cloudflare با حالت Flexible است

جزئیات خطا در `/var/log/hamgam-install.log` است.

**سایت بالا نمی‌آید.** این‌ها را ببینید:

```bash
sudo nginx -t && sudo tail -40 /var/log/nginx/hamgam.error.log
```

**بعد از به‌روزرسانی چیزی خراب شد.** بازگردانی:

```bash
sudo bash deploy/install.sh --rollback
```

**سرور کم‌حافظه.** روی سرور حدوداً ۱ گیگابایتی، محدودکردن heap نود به‌تنهایی
جلوی کمبود حافظهٔ سیستم را نمی‌گیرد. از نسخهٔ `2.1.0`، نصب‌کننده پیش از نصب
وابستگی‌های برنامه، رم و swap آزاد را با محدودیت‌های قابل‌مشاهدهٔ `cgroup v2`
می‌سنجد. اگر رم کمتر از ۱۵۳۶ مبی‌بایت و swap قابل‌استفاده کمتر از ۱۰۲۴ مبی‌بایت
باشد، ساخت را شروع نمی‌کند. این شرط، تضمین موفقیت ساخت در هر شرایطی نیست.

برای اجازه‌دادن به ساخت swap، در همان پوشهٔ مخزن اجرا کنید:

```bash
sudo bash deploy/install.sh --swap=auto
```

برای به‌روزرسانی نصب کامل‌شده:

```bash
sudo bash deploy/install.sh --update --swap=auto
```

- پیش‌فرض `--swap=off` است؛ حتی `--yes` و اجرای غیرتعاملی اجازهٔ ساخت swap نمی‌دهند.
- اگر swap آزاد کافی وجود داشته باشد، فایل تازه‌ای ساخته نمی‌شود.
- در صورت نیاز، یک فایل ۲ گیبی‌بایتی در
  `/var/lib/hamgam-build-swap/swapfile` ساخته و فعال می‌شود. فقط `ext4` و XFS
  پذیرفته می‌شوند و پس از تخصیص باید دست‌کم ۲ گیبی‌بایت فضای دیسک باقی بماند.
- فایل یا پوشهٔ موجود، پیوند نمادین یا مسیر با دسترسی ناامن بازنویسی نمی‌شود.
  در کانتینر، cgroup محدود یا حسابداری نامشخص حافظه، ساخت خودکار swap انجام نمی‌شود.
- **swap پس از موفقیت یا شکست نصب فعال می‌ماند.** نصب‌کننده نه swap موجود را
  خاموش می‌کند، نه `fstab` را تغییر می‌دهد. پس از راه‌اندازی دوباره، این فایل
  خودکار فعال نمی‌شود ولی همچنان روی دیسک است. آن را در حالت فعال حذف نکنید.
- اگر اجرای قبلی فایل را فعال کرده باشد، اجرای مجدد از swap آزاد موجود استفاده
  می‌کند. اگر پوشه باقی مانده ولی فایل فعال نیست، نصب‌کننده توقف می‌کند تا مسیر
  را دستی بررسی کنید؛ فایل قبلی را حذف یا بازنویسی نمی‌کند.

**راه جایگزین بدون ساخت روی سرور.** روی رایانه یا CI بسازید:

```bash
APP_BASE=/ npm run build
```

پوشهٔ `dist` را روی سرور منتقل کنید و هنگام نصب حالت `prebuilt` را انتخاب کنید
یا مسیر آن را بدهید:

```bash
sudo bash deploy/install.sh --source prebuilt --dist /srv/hamgam-dist
```

حالت `prebuilt` و بازگردانی نسخه، swap را آماده یا تغییر نمی‌دهند. خروجی پیش‌فرض
GitHub Pages برای ریشهٔ دامنه مناسب نیست؛ حتماً با `APP_BASE=/` بسازید.

**پیام `Killed` هنگام ساخت.** احتمال کمبود حافظه زیاد است، اما این پیام یا حتی
کد خروج `137` به‌تنهایی OOM را ثابت نمی‌کند. کد واقعی دستور و وضعیت حافظه پیش و پس
از شکست در لاگ نصب ثبت می‌شود. برای شاهد کرنل:

```bash
sudo journalctl -k --since "20 minutes ago" --no-pager
```

به پیام‌های `Out of memory`، `Killed process` و شمارندهٔ `oom_kill` در لاگ توجه
کنید. اگر شکست پیش از استقرار رخ داده، نسخهٔ زنده جابه‌جا نشده است؛ نصب اولیهٔ
ناموفق را بدون `--update` دوباره اجرا کنید.

## دادهٔ کاربران

بکاپ این اسکریپت **فقط فایل‌های برنامه** است، نه دادهٔ کاربران. دادهٔ هر کاربر
در IndexedDB مرورگر خودش می‌ماند و روی سرور هیچ نسخه‌ای از آن نیست. اگر دامنه
را عوض کنید یا از HTTP به HTTPS بروید، دادهٔ مرورگر منتقل نمی‌شود؛ برای جابه‌جایی
از قابلیت پشتیبان‌گیری داخل خود برنامه (تنظیمات ← پشتیبان‌گیری) استفاده کنید.
