# نصب روی سرور اختصاصی (Ubuntu/Debian)

این پوشه یک نصب‌کنندهٔ تعاملی دارد که «همگام» را روی سرور خودتان بالا می‌آورد:
دامنه، گواهی SSL رایگان، nginx، فشرده‌سازی، هدرهای امنیتی و کش درست؛ همه
به‌صورت خودکار، با تست سلامت در پایان.

اگر GitHub Pages برایتان کافی است، به این پوشه نیازی ندارید.

---

## چرا سرور اختصاصی؟

|                    | GitHub Pages      | سرور اختصاصی         |
| ------------------ | ----------------- | -------------------- |
| راه‌اندازی         | آماده             | یک بار اجرای اسکریپت |
| دامنهٔ اختصاصی     | ممکن است          | کامل، با SSL خودکار  |
| سرو از ریشهٔ دامنه | نه (زیرمسیر)      | بله                  |
| کنترل هدرها و کش   | محدود             | کامل                 |
| به‌روزرسانی        | خودکار با هر push | `--update`           |

هر دو کاملاً کار می‌کنند؛ سرور اختصاصی کنترل بیشتری می‌دهد.

---

## پیش‌نیازها

- سرور Ubuntu ۲۲.۰۴ یا ۲۴.۰۴ (یا Debian ۱۲) با دسترسی root یا `sudo`
- دامنه‌ای که رکورد `A` آن به IP سرور اشاره کند
- پورت‌های ۸۰ و ۴۴۳ آزاد (اگر Apache دارید، اول متوقفش کنید)
- حدود ۱٫۵ گیگابایت فضای دیسک آزاد

HTTPS اجباری است، نه اختیاری: بدون HTTPS مرورگر سرویس‌ورکر را ثبت نمی‌کند،
پس حالت آفلاین و «افزودن به صفحهٔ اصلی» کار نمی‌کند.

## اجرا

مخزن را روی سرور بگیرید و اسکریپت را اجرا کنید:

```bash
git clone https://github.com/saeedgh837/fit-tracker-pwa.git && cd fit-tracker-pwa && sudo bash deploy/install.sh
```

اسکریپت این مقادیر را می‌پرسد و برای هرکدام پیش‌فرض پیشنهاد می‌دهد:

- **دامنهٔ سایت**: مثل `fit.example.com` (بدون `https://`)
- **ایمیل**: برای Let's Encrypt؛ فقط برای یادآوری انقضای گواهی
- **مسیر نگهداری نسخه‌ها**: پیش‌فرض `/var/www/hamgam`
- **حالت تأمین سورس**: `git` (پیش‌فرض)، `local` یا `prebuilt`

سپس ۱۰ گام را پیش می‌برد: بررسی سیستم، نصب بسته‌ها، ساخت برنامه، استقرار،
تنظیم nginx، فایروال، گواهی SSL، و ۱۲ بررسی سلامت. اگر همه‌چیز درست باشد،
بنر سبز «نصب با موفقیت کامل شد» را با نشانی سایت می‌بینید.

### حالت‌های دیگر

```bash
sudo bash deploy/install.sh --non-interactive --domain fit.example.com --email me@example.com
```

```bash
sudo bash deploy/install.sh --update
```

```bash
sudo bash deploy/install.sh --rollback
```

`--help` فهرست کامل گزینه‌ها را نشان می‌دهد.

## ساختار استقرار

فایل‌ها هرگز مستقیم روی نسخهٔ زنده کپی نمی‌شوند:

```
/var/www/hamgam/
├── releases/
│ ├── 20261019-010203-a1b2c3d/ ← یک نسخهٔ کامل و مستقل
│ └── 20261018-220904-819575b/ ← نسخهٔ پیشین
├── current -> releases/20261019-... ← پیوند اتمیک؛ ریشهٔ nginx همین است
└── .previous ← نسخه‌ای که --rollback به آن برمی‌گردد
```

چرا این‌قدر مهم است:

- **هیچ‌وقت نسخهٔ نیمه‌کپی‌شده روی سایت نیست.** هر اجرا اول یک نسخهٔ کامل
  می‌سازد و بعد پیوند را جابه‌جا می‌کند. جابه‌جایی پیوند یک عملیات اتمیک است.
- **تب‌های باز نمی‌شکنند.** فایل‌های هش‌دار نسخهٔ پیشین در نسخهٔ تازه نگه
  داشته می‌شوند، پس اگر کاربری هنوز نسخهٔ قدیمی را اجرا می‌کند و یک chunk
  تنبل را می‌خواهد، ۴۰۴ نمی‌گیرد.
- **بازگردانی خودکار.** اگر بعد از جابه‌جایی هر خطایی رخ دهد، اسکریپت خودش
  به نسخهٔ پیشین برمی‌گردد.
- **پاک‌سازی امن.** فقط چند نسخهٔ آخر می‌مانند، و نسخهٔ فعال و هدف بازگردانی
  هرگز پاک نمی‌شوند.

## فایل‌هایی که ساخته می‌شود

| مسیر                                      | چیست                            |
| ----------------------------------------- | ------------------------------- |
| `/var/www/hamgam/`                        | نسخه‌ها و پیوند `current`       |
| `/etc/nginx/sites-available/hamgam`       | کانفیگ سایت                     |
| `/etc/nginx/snippets/hamgam-headers.conf` | هدرهای امنیتی                   |
| `/etc/nginx/conf.d/hamgam-cache.conf`     | سیاست کش                        |
| `/etc/hamgam/install.conf`                | تنظیمات نصب (فقط root، مود ۶۰۰) |
| `/var/log/hamgam-install.log`             | لاگ کامل نصب                    |

تنظیمات ذخیره‌شده هیچ رمز یا کلیدی ندارد.

## نکات امنیتی و رفتار محافظه‌کارانه

اسکریپت عامدانه در چند جا محافظه‌کار است:

- **فایروال را خودش روشن نمی‌کند.** روشن‌کردن `ufw` می‌تواند دسترسی SSH را
  قطع کند. اگر `ufw` فعال باشد فقط پورت‌های ۸۰ و ۴۴۳ را باز می‌کند.
- **کانفیگ پیش‌فرض nginx را بی‌اجازه حذف نمی‌کند.** ممکن است سرویس دیگری از
  آن استفاده کند؛ تایید می‌گیرد و راه بازگردانی را چاپ می‌کند.
- **کانفیگی که certbot نوشته را با قالب HTTP بازنویسی نمی‌کند**، وگرنه گواهی
  بی‌اثر می‌شد.
- **`npm ci` و build را با کاربر غیرریشه اجرا می‌کند.** اسکریپت‌های lifecycle
  وابستگی‌ها نباید دسترسی root بگیرند.
- **nginx از snap را تشخیص می‌دهد و پیش از هر تغییری متوقف می‌شود**، چون دو
  نصب موازی nginx سرور را خراب می‌کند.
- **مسیرهای سیستمی را نمی‌پذیرد.** `/`، `/etc`، `/usr` و مانند آن‌ها رد
  می‌شوند تا اشتباه تایپی به پاک‌شدن فایل‌های سیستمی منجر نشود.
- **هر اجرا قفل می‌شود** تا دو اجرای همزمان با هم تعارض نکنند.

### Cloudflare

اگر دامنه پشت پروکسی Cloudflare است:

- حالت SSL را روی **Full (strict)** بگذارید، نه Flexible. با Flexible،
  Cloudflare به سرور شما HTTP حرف می‌زند و ریدایرکت HTTPS بی‌پایان می‌شود.
- برای گرفتن گواهی با DNS-۰۱:

```bash
sudo certbot certonly --dns-cloudflare --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini -d fit.example.com
```

فایل مجوز باید فقط برای root خواندنی باشد:

```bash
sudo chmod 600 /etc/letsencrypt/cloudflare.ini
```

- بررسی DNS در اسکریپت فقط **تشخیصی** است و جلوی گرفتن گواهی را نمی‌گیرد،
  چون پشت Cloudflare یا NAT آدرس دیده‌شده با IP سرور یکی نیست.

## تست‌ها

```bash
bash deploy/install.test.sh
```

تست‌های واحد برای توابع خالص و کانفیگ تولیدشده: اعتبارسنجی ورودی، جابه‌جایی
اتمیک، بازگردانی، مهاجرت از چیدمان قدیمی، نگه‌داشتن asset های نسخهٔ پیشین،
پاک‌سازی نسخه‌ها، و اعتبارسنجی خروجی build.

اجرای واقعی روی اوبونتو در ورک‌فلوی `installer.yml` انجام می‌شود: نصب کامل با
apt و nginx واقعی، بررسی سایت زنده، اجرای دوباره برای اثبات idempotent بودن،
به‌روزرسانی، بازگردانی، و زنده‌ماندن سایت بعد از ری‌استارت nginx.

## عیب‌یابی

**گواهی گرفته نشد.** اسکریپت در پایان صریح می‌گوید. معمولاً یکی از این‌هاست:

- رکورد A دامنه به این سرور اشاره نمی‌کند
- پورت ۸۰ از بیرون بسته است (فایروال ابری یا NAT)
- دامنه پشت Cloudflare با حالت Flexible است

جزئیات خطا در `/var/log/hamgam-install.log` است.

**سایت بالا نمی‌آید.** این‌ها را ببینید:

```bash
sudo nginx -t && sudo tail -40 /var/log/nginx/hamgam.error.log
```

**بعد از به‌روزرسانی چیزی خراب شد.** بازگردانی:

```bash
sudo bash deploy/install.sh --rollback
```

**روی سرور کم‌حافظه (۱ گیگابایت) ساخت ناکام می‌ماند.** از خروجی آمادهٔ CI
استفاده کنید یا اول swap بسازید:

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
```

## دادهٔ کاربران

بکاپ این اسکریپت **فقط فایل‌های برنامه** است، نه دادهٔ کاربران. دادهٔ هر کاربر
در IndexedDB مرورگر خودش می‌ماند و روی سرور هیچ نسخه‌ای از آن نیست. اگر دامنه
را عوض کنید یا از HTTP به HTTPS بروید، دادهٔ مرورگر منتقل نمی‌شود؛ برای جابه‌جایی
از قابلیت پشتیبان‌گیری داخل خود برنامه (تنظیمات ← پشتیبان‌گیری) استفاده کنید.
